Configuration settings#

Reference — a description of the machinery. Look things up here.

Every environment variable the backend reads, found by scanning the source rather than by importing it — a variable read inside a function body is never reached by an import, so only the source knows the whole set.

449 settings. 20 are declared in backend/config_registry.py, which is the set rackstatus.toml can carry, the required- setting preflight can demand, and rackstatus.toml.example lists. 210 are named in docs/ENVIRONMENT.md — named, which is a weaker claim than explained: the check is whether that document mentions the setting at all. It is not in this site yet; see docs/README.md for why the migration is page-at-a-time.

How a value is resolved#

Highest wins (core-designs.mdc §5):

  1. the active cluster’s high overlay — identity, naming and connection from the catalog

  2. job env overrides — var/cache/job_env_overrides.json, written by the Settings screen

  3. the process environment — rackstatus.toml, the shell, the container

  4. the platform’s low overlay — geometry and per-tool defaults

Reader below says which rung a setting starts at. ladder means it is read through _eget and therefore honours all four; environment means it is read straight from the process environment and cannot be set per cluster or from the Settings screen.

Declared, read indirectly#

4 settings are declared but never appear in a call this scan can see: the connection profile reads its four by name from a list, and NVIS_LOG_LEVEL goes through logging_config’s own registry. They are configuration like any other — the scan simply cannot point at a call site.

NVIS_LOG_LEVEL, RACK_SSH_KEY, RACK_SSH_PORT, RACK_SSH_USER

Read outside the resolution ladder#

296 of them are read only via os.environ, so a cluster overlay and the Settings screen cannot influence them — the setting is process-wide. New code should prefer _eget (core-designs.mdc §5); these are the ones that predate the rule or genuinely belong to the process rather than to a cluster.

They are not listed here — 296 names in a paragraph is not something anyone reads. The table below marks each one environment in its Reader column, which answers the same question setting by setting, where you are already looking.

Every setting#

What it controls is the registry’s own description where a setting has a declaration, then a reviewed hint from docs/settings-hints.toml, then a pointer to the prose in docs/ENVIRONMENT.md. A dash means nobody has written one yet.

Reader is ladder where the value goes through _eget, environment where it is read straight from os.environ, and indirect for the five consumed by name from a list (the connection profile) or through another registry (logging_config) rather than by a call this scan can see.
